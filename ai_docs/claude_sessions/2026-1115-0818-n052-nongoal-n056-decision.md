## N-052: `round(int)`'s result type → Non-goals

- `round/ceil/floor/trunc/sign` of an integer keep returning **bigint**.
  Postgres returns double precision, but the values agree. Switching
  would change the type embedded Go callers read (int64 → float64) for
  no value change, and a client written for Postgres already reads the
  bigint.

## N-056: drops cascade "the same as Postgres, if that works for us"

Recorded as the item's decision, with a build checklist. Not built yet.

- `DROP COLUMN` drops every index that includes the column, with no
  CASCADE needed, multi-column indexes included. With CASCADE, a
  foreign-key constraint on the column goes too.
- `DROP TABLE … CASCADE` drops the foreign-key constraints of other
  tables that reference it, not the tables themselves, with Postgres's
  `drop cascades to constraint x on table y` notice. Dependent views go
  too, if bytdb can tell which views depend on the table. Without
  CASCADE it stays refused (2BP01).
- Each drop runs as one DDL transaction, so a failure leaves nothing
  half-dropped.
- Afterwards, update the RESTRICT-only wording: the D-54 paragraph in
  `docs/features.md`, `docs/gotchas.md`, the 2BP01 comment in
  `pgwire/errors.go`, and the parser's `dropBehavior` comment. Remove the
  work-around in `TestGormVerbatim`, which drops the index and the child
  first.
- Check each behavior against PG16 (docker `bytdb-numeric-pg`, 55432)
  before building it.

This reverses deep-look D-54's "remove the dependent object first" rule
for these cases. The motive is GORM's `Migrator.DropColumn` and its
parent-first `DropTable`, both captured in N-049.
