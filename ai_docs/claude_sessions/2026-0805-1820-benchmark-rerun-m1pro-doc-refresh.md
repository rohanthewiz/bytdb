# Benchmark re-run on M1 Pro + doc refresh

Session: f200f643-e5a3-49ac-bdd7-bdc1c93c43ae
Date: 2026-08-05
Follows: 2026-0805-1603-correlated-subquery-index-pushdown.md

## What happened

Re-ran every benchmark suite that feeds published numbers and updated
all docs that cite them. All three suites ran sequentially (never
concurrently) to avoid CPU-contention skew. Nothing regressed; the
recent perf-pass improvements are now visible in the published scan
numbers.

Machine note: the README's head-to-head and OCC tables were previously
measured on an Apple M3; this machine is an **Apple M1 Pro, 16 GB**
(macOS 26.5.1, Go 1.26.1). Absolute numbers mostly rose a little with
the hardware change; every doc's machine/date note now says 2026-08-05,
Apple M1 Pro.

## Suites run

1. **bench/head2head.sh** — 8 parallel writers vs Badger, SQLite
   (mattn + modernc), Bolt, Redis, DuckDB; medians of 3.
2. **Root OCC self-comparison** — `BenchmarkIdentityInsertParallel`,
   `BenchmarkIdentityInsertHeavyTxn`, `BenchmarkSerializableHeavyTxn`
   (-cpu 8 -count 3), plus btypedb's `BenchmarkParallelUpdates*`
   from the sibling ../btypedb checkout.
3. **bench/run.sh latency suite** — bytdb always/lazy/pgwire vs
   Dockerized tmpfs Postgres 16.14, DuckDB (go-duckdb v2.4.3),
   Redis 7.0.0. Needed `GOWORK=off go mod tidy` in bench/ first
   (bytdb require bump v0.7.0 → v0.8.0 to match the checkout);
   run.sh was also missing its execute bit (fixed, mode committed).

## Headline results (medians)

Head-to-head (insert / 400-reads+insert): Badger 4.2/146 µs,
SQLite-mattn 8.1/1,212, SQLite-modernc 11.7/2,118, bytdb
single-writer 14.3/189, bytdb OCC 14.7/**51**, Redis 21.9/222,
Bolt 36.7/106, DuckDB 97.9/10,015. bytdb OCC still wins the heavy
shape outright — now **24×** ahead of the fastest SQLite (was 14×).
Ordering changes vs the M3 run: single-writer now edges OCC on plain
inserts, and Redis inserts beat Bolt here.

OCC self-comparison: identity insert at parity (14.6 vs 14.8 µs);
400-read SQL txn — OCC 79 µs vs single-writer 195 µs (**2.5×**),
serializable 101 µs (1.9×); btypedb heavy (2000 reads + 5 random
writes) — **5.1×** (125 vs 634 µs), consistently fast this run
(124–131 µs all three samples; footnote now says conflict-dependent
rather than bimodal, citing earlier ~2× sessions); light 20-read
shape still loses under OCC (30.4 vs 24.6 µs).

Latency suite: durable solo commit 3.9 ms; SyncEverySecond insert
18.8 µs; embedded point read 5.2–5.6 µs; pgwire point read 39.6 µs;
full-scan aggregate improved **31 → 26.4 ms** (the perf pass showing
up). Postgres/DuckDB/Redis numbers moved only modestly.
