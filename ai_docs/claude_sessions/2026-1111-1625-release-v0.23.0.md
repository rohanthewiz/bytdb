## The red Linux CI job

Before tagging, `gh run list` showed the Linux `test` job (and the
`btypedb-main` canary, which runs the same tests) failing on **every push
since D-15** (2026-11-10, `bcbad02`). The scheduled runs looked green
only because they run the fuzz jobs alone. Always the same test, always
"stream cut after ~1.2 s and ~2.6 MB: EOF"; macOS never failed.

- Reproduced locally with Docker: `golang:1.26.1` container mounting
  `bytdb` and `../btypedb` (the `go.work` needs both), named volumes for
  the module and build caches. 5/5 failures.
- First hypothesis (receive-window hysteresis on the client) was wrong:
  clamping the client's `SO_RCVBUF` alone still failed 20/20.
- Actual cause, on the sender side: a Go `Write` blocked on a full socket
  waits for EPOLLOUT, which Linux raises only when free send space is at
  least half the queued bytes (`sk_stream_is_writeable`), i.e. after about
  a third of the send buffer drains. The buffer autotunes to `tcp_wmem`'s
  max (4 MiB in the container), so at the test's ~2-3 MB/s the wake-up
  takes over a second, which is longer than the test's 300 ms
  WriteTimeout. The server's per-write stall deadline (D-15b) works as
  written; "progress" is just coarse as the server sees it.
- Fix in the test: `sndbufListener` sets `SO_SNDBUF` = 64 KiB on accepted
  conns (via a new `startWriteTimeoutServerOn(t, wt, wrap)` hook; the old
  `startWriteTimeoutServer` delegates to it), and the client clamps
  `SO_RCVBUF` too. 30/30 on Linux, full `-race` suite green in the
  container, and CI run `43101996263` green on every job but the
  allowed-to-fail `pgwire-released-pin`.
- Production note added to `Server.WriteTimeout`'s doc: at the 60 s
  default, a client draining slower than ~20 KB/s can be cut even though
  it never stopped. That is acceptable for now and was not raised as an item.

From a scratch dir outside any checkout, `GOWORK=off`:
`go install github.com/rohanthewiz/bytdb/pgwire/cmd/{bytdb,bytdbd}@latest`
and `go run …/cmd/bytdbd@latest -h`, once with
`GOPRIVATE=none.invalid GOPROXY=https://proxy.golang.org`, once with the
default env (GOPRIVATE covers `github.com/rohanthewiz/*`). Both installed,
`go version -m` shows pgwire v0.23.0, bytdb v0.23.0, btypedb v0.10.0. The
"requires go >= 1.26.1; switching to go1.26.11" line is the toolchain
auto-switch outside the repo, harmless.

`pgwire-released-pin` stays allowed-to-fail by design: it fails whenever
pgwire uses root API newer than the last tag (the N-031 trade-off).

## Gotchas learned

- A background "wait for CI" loop using `gh run list -c <sha>` got an empty
  run id and polled forever; `-c` filters by commit but returned nothing
  here. Find the run by `headSha` from `gh run list --json` instead.
- `gh run list` on main showing "success" for scheduled runs means little:
  those runs skip every job but fuzz.
