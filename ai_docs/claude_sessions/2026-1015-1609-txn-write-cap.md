# Transaction write cap: refuse a runaway transaction instead of OOM

- **Session:** `dc3e7c32-ec24-46ec-a4ef-0a340af785be`
- **Date:** 2026-10-15
- **Scope:** N-028 from the next-list, dropped in from the cats-todo
  backlog: bound the number of writes one transaction may stage. This is
  point 2 of the OOM gap analysis from `2026-1015-0809-memory-ceiling-result-row-cap`.
  Points 1 and 3 were the result row cap and the memory ceiling.
  **Not released:** the latest tags are still v0.21.2 / pgwire/v0.21.2,
  and `bytdbd` uses the new symbols, so pgwire builds only through
  `go.work` until `/release` bumps its pin.

## 1. Measurement that settled the DELETE question

A throwaway test staged 200k writes in one `Txn` on a 3-column
unindexed table and read `HeapAlloc` after two GCs before commit:

| write  | staged heap per row |
|--------|--------------------:|
| insert | ~377 B |
| update | ~345 B |
| delete | ~32 B  |

A delete stages a key-only WAL record and a tree that shrinks, about a
tenth of an insert's cost. Deleting is also how an operator frees space,
which is why the memory ceiling already exempts it. **Decision:** DELETE
and TRUNCATE do not count. ALTER rewrites stay under `SetBackfillLimit`.

## 2. The default: 10M, not 1M

`DefaultMaxTxnWrites = 10_000_000`, the same as `DefaultMaxResultRows`.
The 1M backfill cap was deliberately not copied: dbc's `sql.write`
("Loads the rows into a table, in one transaction") would break on any
table over 1M rows, and a few million is an ordinary load. 10M is 3.5 to
10 GB staged, so it still stops a whole-table UPDATE on a big table or a
loader that never commits. Small hosts should set `GOMEMLIMIT` (the
ceiling then stops the transaction first) or lower the cap. This is a
behavior change for anyone who stages more than 10M writes in one
transaction today.

## 3. Implementation

- **`memguard.go`**: `ErrTxnTooLarge` ("transaction write limit
  exceeded"), `DefaultMaxTxnWrites`, `SetMaxTxnWrites` / `MaxTxnWrites`
  (0 or less disables, as with `SetBackfillLimit`), and `txnTooLargeErr`,
  whose `hint` field names the batching recipe (one `UPDATE … WHERE id >=
  $1 AND id < $2` per key range, or COMMIT between load chunks). The file
  header now describes three admission controls.
- **`engine.go`**: `maxTxnWrites atomic.Int64`, stored at Open.
- **`txn.go`**: the count lives on `Txn` (`writes int64`), not in
  `insertRow` / `updateRow` as the item suggested, because those take a
  raw kv `Tx` and only `Txn` lasts as long as a transaction. Charged in
  `InsertReturning` / `UpdateReturning`: checked before the write,
  counted after it is staged. A failed insert and an update that matches
  no row cost nothing. At the cap, even an update that would match
  nothing is refused, because the check runs before the lookup.
  One-shot `Engine.Insert` / `Update` write a single row and cannot hit
  the cap. New `Txn.CheckWrites(n)` and `Txn.Writes()`.
- **Savepoints**: `bytdb.Savepoint` is an alias for btypedb's type, so
  the count cannot be a field on it. `Txn.saveWrites` mirrors the kv
  savepoint stack as `{sp, writes}` pairs. `RollbackTo` restores the
  count and truncates the stack above the mark; `Release` pops the mark
  and everything above it. The SQL session's SAVEPOINT / ROLLBACK TO go
  through these wrappers, so a block that retries a batch after ROLLBACK
  TO isn't counted twice.
- **`sql/exec.go`**: `execUpdate` calls `tx.CheckWrites(len(rows))` in
  its pre-write scan callback, so an UPDATE over the cap fails before it
  stages anything or materializes the rest of the table. `execInsert`
  checks `len(s.Rows)` up front when there is no ON CONFLICT. With ON
  CONFLICT the row count is only an upper bound, because DO NOTHING
  writes nothing, so the per-row charge decides. (The SQL layer has no
  INSERT ... SELECT. An early draft of the hint mentioned it and was
  corrected.)
- **pgwire**: `sqlstate` maps "transaction write limit exceeded" to
  54000. `bytdbd -max-txn-writes` (default `bytdb.DefaultMaxTxnWrites`).
- **Docs**: README (Monitoring memory, now "Three guards"), `docs/gotchas.md`
  (Sizing; replaced the "no row cap yet" bullet), `docs/security.md`
  flag table.

## 4. Tests

- `txnwrites_test.go`: default value. What counts: a duplicate insert,
  an update that matches no row, and deletes are not charged, and a
  transaction commits fine after a refusal. Savepoints: ROLLBACK TO
  gives writes back and destroys later marks, a mark survives a
  rollback to it, and Release keeps the count and empties the mirror.
  WriteTxn is capped and rolls back. One-shot writes are never capped.
  CheckWrites, and the cap disabled with 0.
- `sql/txnwrites_test.go`: a whole-table UPDATE is refused with no rows
  changed. A multi-row INSERT is refused whole. ON CONFLICT DO NOTHING
  is not over-charged. DELETE is exempt. In a BEGIN block the count
  spans statements and a refusal aborts the block. ROLLBACK TO gives
  writes back.
- `pgwire/errors_state_test.go`: a mapping case, plus a real UPDATE in
  `TestResourceErrorsEndToEnd` that must come back as 54000.
- Full suites green: root, sql, stdlib, replicate, tuple, pgwire,
  bytdbd. `go vet` clean, including bench.

## 5. Noticed, not done

`execUpdate`'s pre-write `rows` slice never calls `budget.check`, so the
result row cap and the periodic `CheckMemory` poll do not apply to it.
The write cap now bounds it by default. Raised as N-029.
`execDelete`'s collection is unbudgeted too, which may be deliberate
given DELETE's exemption from the ceiling.
